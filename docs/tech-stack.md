# Tech Stack & Key Technical Decisions

**Status:** accepted · **Date:** 18 Nov 2026 · Requirements: [requirements.md](requirements.md)

## Stack

| Layer | Choice |
|---|---|
| Language | TypeScript (strict) in both packages |
| API | NestJS 12 (ESM), REST, Swagger/OpenAPI; request validation with Zod through Nest's `StandardSchemaValidationPipe`; one schema gives validation, types and the Swagger document (confirmed by the login endpoint's Swagger tests) |
| Database | PostgreSQL 16 with Prisma (migrations + typed client) |
| Auth | Short-lived JWT access token + rotating opaque refresh token (httpOnly cookie), argon2id passwords, global guard with `@Public()` opt-outs, `HR_ADMIN` role guard, ownership checks in the service layer |
| UI | React + Vite, Material UI (MUI, decision 15; theme, font and structure, decision 17), TanStack Query, Axios (decision 16), Recharts |
| Tests | Vitest in both packages: + Supertest for the API, + Testing Library for the UI |
| Quality | oxlint for both packages (Nest 12's default, and Vite's), Prettier, Husky + lint-staged, commitlint, GitHub Actions |
| Hosting | Neon (Postgres), Render (API), Vercel (UI) |

## Decisions and trade-offs

1. **Postgres, not SQLite.** The insights (median / P25 / P75 by country, department, level) need `percentile_cont` and window functions so aggregation stays in the database (requirements §5). It also gives exact `NUMERIC` for money and safe concurrent bulk updates. *Cost:* a hosted database is needed for deployment (Neon free tier).
2. **Prisma, with raw SQL where it must.** Prisma gives typed queries and migrations; percentile aggregations go through `$queryRaw`. *Cost:* those queries lose some type safety, so they live in one repository class and are covered by integration tests.
3. **Money is `Decimal`, never float.** Salaries are stored in local currency; USD comparisons use a dated exchange-rate table so numbers are reproducible.
4. **Layered modules: controller → service → repository.** Controllers handle HTTP and validation, services hold business rules and authorisation, repositories own Prisma. Domain rules (tenure band, compa-ratio, annualised growth, band checks) are pure functions, so most unit tests need no database and run in milliseconds.
5. **REST, not GraphQL.** The screens map to a small, known set of queries; REST plus Swagger is simpler to document, test and cache.
6. **React + Vite, not Next.js.** The API is a separate NestJS service, so server-side rendering adds nothing. A static SPA is simpler to build and host. The API does the paging, sorting and filtering (at most 100 rows a page), so the browser never holds the 10,000 employees.
7. **One repo, two independent packages** (`backend/`, `frontend/`, no npm workspaces). One link to submit and one commit history covering API and UI together. Each folder deploys on its own via the host's root-directory setting.
8. **Test strategy.** Many fast unit tests (pure domain logic, services with mocked repositories); a few integration tests against real Postgres for migrations, raw SQL and pagination; component tests for the UI. Domain logic is written test-first. CI runs everything on each push using a Postgres service container.
9. **Performance is measured, not assumed.** Targets are < 500 ms for the directory and < 1 s for insights at 10k employees. They will be checked against the 10k seed with `EXPLAIN`, and indexes added only where the plan shows a need.
10. **Access JWT plus rotating refresh token.** A 15-minute JWT is checked without touching the database. A 7-day opaque refresh token is stored only as a SHA-256 hash, rotated on every use, and a replayed token revokes its whole family. It travels in an httpOnly cookie so scripts cannot read it. *Cost:* an access token cannot be revoked before it expires, and a cookie needs the UI and API to share an origin (see [architecture.md](architecture.md) section 5). A plain long-lived JWT would be simpler, but one leaked token would be valid for days with no way to cut it off.
11. **argon2id for passwords.** OWASP's first choice, and it resists GPU cracking better than bcrypt. *Cost:* a native module, so the Render build must be checked.
12. **Repositories wrap Prisma, and stay thin.** Services never call Prisma directly. Each module has a repository class that owns its queries (`UsersRepository`, `RefreshTokensRepository`). Reasons:
    - **Fast, deterministic service tests.** A service test hands the service a fake repository (`{ findByEmail: vi.fn() }`), so it needs no database and no knowledge of how Prisma's calls are shaped. The `AuthService` unit tests work this way.
    - **One home for the hard queries.** The percentile insights and the filtered, paginated directory over 10,000 rows are raw SQL or complex Prisma calls. In a repository they sit in one place, and integration tests run them against the real database.
    - **Atomic writes.** An interactive transaction needs the Prisma client, which services never touch. So a step that must be all-or-nothing is one repository method: `RefreshTokensRepository.rotate` retires the old refresh token and stores its replacement in one transaction, and returns false if the token was already retired. The rule about what that means (a replay, so revoke the family) stays in `AuthService`. The integration tests run these methods on a rolled-back transaction, where `$transaction` joins the surrounding one.

    *Cost:* Prisma Client is already typed, so a simple method such as `findByEmail` is a one-line pass-through. Repositories also return Prisma's generated types, not separate domain classes, so services stay coupled to those types. Both are accepted: separate entity classes and mappers would double the model code for no gain at this size. *Rules that keep it cheap:* a repository holds queries and no business rules; there is no generic `BaseRepository<T>`, which would hide Prisma's typed API; a method is added only when a service needs it.

13. **Seed data from faker, with the shape decided by us.** `@faker-js/faker` (pinned to an exact version, a dev dependency used only by `npm run seed`) supplies the random choices and the names, in each country's own locale. What makes the data useful is not random rows but their structure, which is plain data in `src/seed/reference-data.ts`: country, department and level weights, a job title ladder per department, tenure that rises with level, about 6% leavers, and fewer women in engineering and at senior levels. *Costs:* faker's output for a given seed can change between versions, so the version is pinned and bumping it changes the dataset (a first version of the seed used hand-written name lists and a tiny random generator of its own, which cannot drift; the author asked for faker, which gives more varied, realistic names for 15 locales for free). Faker has no Latin-script option for Japan, the UAE or Singapore, so those countries get names in their own script, and a search typed in Latin letters will not find them; changing a country's locale is a one-line edit.

14. **Salary history from a stated pay model, one random source per employee.** The seeded pay comes from a model in plain data (`src/seed/pay-model.ts`: a US ladder by level, times a country pay index, a department factor and a fixed illustrative exchange rate, to 3 significant figures), so the numbers are arguable and every insight can be checked by hand. Today's salary is made first and the history is built backwards from it, so the current pay is exactly the model's. Each employee's history is drawn from a small seeded generator keyed by the seed and the employee code (`src/seed/random.ts`), not from faker or from one shared stream. Reasons: (1) the 10,000 employees already stored must not change, and a shared stream would shift every employee after the first difference; (2) the history of one person never depends on who else was generated, so it can be rebuilt for any stored employee and a test can prove it; (3) a faker upgrade cannot change the salaries. *Costs:* a 20-line generator of our own to trust (mulberry32 with a murmur3-style key mix; tests check its spread and that neighbouring keys do not correlate), and amounts are whole currency units rounded to 4 significant figures, which is coarser than real pay but exact (money is never a float in the database). The seed only reads stored employees and inserts for those with no record, scoped to the numbered `EMP-` set, so it never invents pay for an employee created later in the app.

15. **Material UI for the UI: the author's choice, not a measured one.** (The earlier plan was shadcn/ui + Tailwind + TanStack Table.) Reasons that hold: (1) the author knows MUI well, which shortens the build and lowers the risk of UI defects on a deadline; (2) the UI only ever renders one server-side page of at most 100 rows (the API caps `pageSize` at 100 and nothing loads 10,000 rows), so no library is slow at this size and virtualization is not a criterion; (3) the free MUI X DataGrid caps a page at 100 rows, the same cap as the API (MUI's pagination docs), and has a server mode for paging, sorting and filtering; (4) of the full component libraries compared, MUI is the most downloaded on npm (58.5 million in the month to 20 Nov 2026, against 21.6 million for Ant Design, 15.4 million for Mantine and 9.1 million for Chakra; downloads include CI installs). *Costs:* a larger JavaScript payload than a Tailwind and Radix stack is expected (Emotion's styling runtime plus the components), but a bundle comparison was written and never run, so there was **no measured number** when this was decided (decision 17 has the first one, for the app as built so far); MUI grew more slowly than the headless stack in the same period (+104% against +481% for TanStack Table); and anything beyond the free DataGrid edition is not used, so the filters are our own controls that send the `QUERY /employees` body. *Table component: decided, MUI X DataGrid community edition in server mode* (`paginationMode` and `sortingMode` set to `server`, so the grid only displays the page the API returned). MUI's plain Table was the alternative: a smaller dependency, but sorting headers, pagination, and loading and empty states would be ours to build and test. Installed: `@mui/material` 9.5.0, `@mui/x-data-grid` 9.18.0, Emotion 11.14, `react-router` 8.5.2 and `@tanstack/react-query` 5.108.1; each package's `latest` tag was checked and is a stable release. `@mui/icons-material` is not installed until a screen needs it.

16. **Axios, as one instance, for the API client: the author's choice over `fetch`.** (The first proposal was a small `fetch` wrapper.) What it gives: interceptors put the token on every call and handle a 401 in one place; the instance is created by `createApiClient` in `frontend/src/api/client.ts`, so a test can hand it a fake adapter and no network is needed. The rules the client follows: the access token lives in a variable, never in browser storage (a reload refreshes from the httpOnly cookie); a 401 starts **one** refresh that every concurrent request and the start-up session restore share, because a refresh token works once and reusing it ends the login (React StrictMode runs effects twice in development, which would otherwise do exactly that); a request is retried once and never twice; login and logout are never refreshed, since a 401 there is the answer; the session is reported expired only when the server refuses the refresh cookie (a network error or a 5xx leaves the session alone). Every failure is thrown as an `ApiError` with the HTTP status, so screens never see an axios error. `QUERY /employees` is sent with axios's `method: 'QUERY'`: checked against a mock API through the Vite proxy with both axios transports (Node's `http` and jsdom's `XMLHttpRequest`, which a browser uses), including that the JSON body survives the retry after a refresh; not yet checked in a real browser. *Costs:* an extra dependency (axios 1.21.1; the lockfile gained 22 packages, 0 audit findings) whose own share of the bundle is **not measured** (decision 17 has the total); and the client talks to the API through hand-written copies of the response types, so they must be kept in step with the backend's schemas by hand. *Known limit:* two browser tabs that refresh in the same instant can present the same cookie twice and end the login; the Web Locks API would fix it, and it is not built.

17. **The theme, the font, the folder layout and the sign-in rules.** *Palette:* taken from the author's login design (brand red `#E11B22`, an "ink" `#1F2430` for text and the dark panels, light neutrals), in `frontend/src/theme/palette.ts`. Every text and background pair was checked against WCAG AA by computing the ratios: white on the red is 4.8:1, the red as link text on white 4.8:1, the secondary text colour 5.8:1 on the page background. Three changes to the design, each for a reason: success green is darkened (`#16895A` was 4.4:1, under AA; now `#127A52`, 5.3:1); error is a deeper red (`#B42318`) than the brand, because with a red primary a plain red error would look like another primary action; and a focused field gets the dark ink ring (MUI `color="secondary"`, set as the `TextField` default), because a red focus ring looked exactly like a validation error in the first screenshot. `secondary` means "the neutral ink", never a second accent. *Font:* Mulish, self-hosted as a variable font from `@fontsource-variable/mulish` (the design loaded it from Google Fonts), so a page view makes no third-party request and any weight from 200 to 1000 comes from one file per script; only the scripts a page uses are downloaded (five files are shipped, one is fetched for English text). *Type scale:* body 14px, page titles 24px, an admin tool being denser than MUI's defaults. *Structure:* feature folders, shared components, one `theme/` folder, one route table, one place for paths (see `frontend/README.md`). *Sign-in rules:* the access token is never stored; every page load restores the session from the httpOnly refresh cookie before a route is chosen (no flash of the login page or of protected content); signed-out visitors are sent to `/login` and returned to where they were going; a signed-in user who is not an HR admin sees a no-access page; the browser guard is a courtesy and the API is what enforces access; the data cache is cleared whenever a session ends, so a shared browser keeps nothing of the last user; a failed sign-out keeps the user signed in and says so, because with the refresh cookie still valid, appearing signed out would be untrue; the form refuses to send what the server would refuse (login is rate limited and every attempt counts). *Left out of the design on purpose:* the stats (10,000 employees, 6 countries, 6 currencies) were wrong against the real data (15 countries) and a public page cannot keep numbers true, so three facts that are true of the system today replace them; "SSO, Encrypted, Audited", "Keep me signed in" and "Forgot password?" describe things that do not exist; the support link has no target, so it is plain text. *Measured:* the production bundle for the app as built so far (React, MUI core, Emotion, react-router, TanStack Query, axios) is 643 kB, 205 kB gzipped, in one chunk; it will grow with the DataGrid, and Vite already warns above 500 kB, so code-splitting by route is the next lever. *Not done:* dark mode (the palette is light only), and a real-browser pass through sign-in against the real API.

18. **The employee table.** *What it is:* `EmployeeTable` only displays what it is given (one page of rows, the total, the sort, the page, and whether it is loading or failed) and reports what the user asked for; the API pages, sorts and filters. The MUI X DataGrid runs in server mode, so the browser holds at most 100 rows. *Columns (ten):* Employee (name over its code), Job title, Level, Department, Country, Joined (date over a tenure band such as "3-5 yrs"), Salary (local; amount over its currency code), Salary (USD), Pay band, Status. Two-line cells put facts that belong together in one column so ten columns fit a 1366px laptop screen. Measured with real scrollbars: no horizontal scrollbar from 1366px up (the columns need 1,278px and the grid has 1,301px at 1366px), and at 1280px the grid scrolls sideways by about 63px. Cell padding is 8px a side, not the default 10px, which is what makes it fit. A first check, made with scrollbars hidden, said it already fitted and was wrong: a real vertical scrollbar takes 15px, and the grid then scrolled sideways and clipped "United Kingdom". *Rules the design follows:* the local salary column is not sortable, because ordering amounts in different currencies means nothing, so people sort by the USD column; every other sortable column's `field` is the API's own sort field (a test checks it), so a header click maps straight to `sortBy`; the sort has no "unsorted" state, since the API always sorts; the expected pay-band case ("Within band") is plain muted text so the exceptions (a "Below band" or "Above band" chip, each also named in words) are what the eye finds; people who have left are muted, with the leaving date, and the status never relies on colour alone; a missing value is a dash with the reason as a tooltip; changing the sort or the page size goes back to page 1. *Formatting (`features/directory/format.ts`):* a stored date is a calendar date, not a moment, so it is formatted in UTC (read as local midnight it shows as the day before west of Greenwich), and the tests run in America/Los_Angeles so that bug fails here; the first check of that test used a bug that was self-consistent and caught nothing, and the second, realistic one is what proved it; months are three letters ("Sep", where en-GB gives "Sept"); money arrives as a decimal string and is only formatted (Intl.NumberFormat reads the string exactly), never calculated with; local amounts show decimals only if the stored value has them, US dollars round to whole dollars because that column is for comparing. *A bug only the browser showed:* "next page" went to page 2 and straight back to page 1. The cause was passing the grid a new `paginationModel` and `sortModel` object on every render; keeping them the same between renders (`useMemo`) fixes it. My first theory, that the grid reports a sort change after each page change, was wrong: guarding against that did not fix it, and it was removed. A test that drives the table with real state (the way the page does) reproduces it and fails without the fix; the earlier test passed because its callbacks did not feed back into the table. *Measured:* with the DataGrid the production bundle is 1,211 kB, 372 kB gzipped, in one chunk (643 kB, 205 kB before it), so the grid costs about 570 kB, 170 kB gzipped. *Cost and next lever:* the login page now downloads the grid too; loading the directory page lazily would keep the login page at the earlier size. *Filters (added after the table):* a search box (name or employee ID; the API does not search job titles), Country and Department as multi-selects (the API accepts several values of each), and Status as three buttons, All / Active / Left, because it has two values and a button is one click where a dropdown is two. The option lists come from a small read-only endpoint, `GET /employees/filter-options` (countries with their codes, and departments, ordered by name), chosen over hard-coding them in the browser, where they would drift from the database; job title and level filters are not offered yet. Typing waits 300 ms for a pause before searching; any filter change goes back to page 1; a filter that is set is bold with a darker outline; "Clear filters" appears only when one is set. An unset filter is left out of the request body, because the API answers 400 to an empty list or a blank search. *Not built:* the summary cards above the table, the filters and table state in the URL, opening a person from a row, a layout for phones (this is a desktop admin tool), and a keyboard-only or screen-reader pass over the grid.
19. **The employee profile.** *Shape:* a panel that slides in from the right over the directory (the author's design), not a separate page. It is a route, `/employees/:id`, nested inside the directory's route, so the profile has its own link and a reload or a shared link opens it, while the list behind it stays mounted: the filters, the search text and the page are still there when it closes (a test and a real-browser run check this). Opening it: a click anywhere on a row, or the name, which is a real link so it works from the keyboard and in a new tab (the row ignores clicks that came from the link, so one click is one step in the history). Closing it steps back when it was opened from the list, so the Back button does not bring it back, and goes to the directory when it was opened from a link or a reload. *Contents:* job title, department, country, status (with the leaving date), level, joined date, the salary in its own currency and in US dollars, then the salary history, newest first. *The history:* each step is named by its reason ("Joined ACME" for the hire, "Merit increase", "Promotion", "Market adjustment", "Correction", or "Salary recorded" when a spreadsheet gave none), with its date, the salary before it, who recorded it (the requirement says the history shows who changed it; the seeded history has no one), the amount, and the change as a percentage. A marker shows which salary is in force today (red), which is still to come (a ring and a "Scheduled" label) and which was replaced (grey). *Where the numbers come from:* `GET /employees/:id` returns the same row the directory shows (the SQL that defines it is shared with the list, so the two cannot disagree about the salary in force or the pay band) plus the history. The previous salary, the percentage (rounded to one decimal, in SQL, on exact decimals) and the in-force marker are worked out in one query with a window function, and the percentage is left out when the currency changed, because it would mean nothing. Amounts stay in the currency they were paid in. *Left out on purpose:* the email under the name in the design, because employees have no email (only login accounts do; adding one needs a column, a migration and seed data, and is the author's call); the Edit salary button, which arrives with recording a salary change; an Actions column (the row and the name already open the profile, and ten columns already fill a laptop screen). *Small changes to the design:* Level and Joined added to the details, "by <name>" added to a step, and "Annual revision" is called "Merit increase" to match the reason. *Two things the first screenshots showed:* the grey markers of replaced salaries were almost invisible (the light divider colour on white), and the open dropdowns had a red focus ring, which the theme avoids because red reads as an error (they now use the ink colour like the text fields).
20. **Recording a salary change.** *What it does:* the Edit salary button in the profile panel (shown for active employees only) opens a form: the new annual salary, the date it takes effect (today by default; a future date schedules the change; never before the joining date) and a reason (promotion, merit increase, market adjustment or correction). Saving appends one entry to the history and never edits or deletes one; a mistake is fixed with a later correction entry. *Rules (`salary-change.rules.ts`, pure, written test-first):* no change for someone who has left (409: their history is closed); the date is not before the joining date; HIRE is the reason of a person's first salary and of no other, so someone with no salary yet is offered HIRE alone and everyone else the other four. *The currency is not asked for:* the API records it in the currency in force on the effective date (the latest record up to that date, the earliest record's if the date comes before all of them, the country's currency for a first salary), so a salary is never entered in a currency the person is not paid in. The form shows the person's current currency in front of the amount. *Money:* the amount travels as text, checked as digits with at most two decimals, not zero and at most 12 digits before the dot (the column is `numeric(14,2)`); it is never a JavaScript number, and a test fails if it becomes one. A thousands separator is refused rather than guessed, because "52,000" is 52 thousand in the US and 52 in much of Europe. The form reads back what it will save ("Will be recorded as £52,000.50 a year") so a misplaced decimal point or a dropped zero shows before saving. *Who:* `changed_by` comes from the access token, never from the request body (an e2e test checks it). *After saving:* the API answers with the updated profile, which goes straight into the cache so the panel shows the new history at once, and a confirmation appears; the directory's pages are marked stale and reload, since their salary columns changed. *Not handled:* a correction dated before a change of currency shows the person's current currency in the form while the API uses the one in force on that date (rare: it needs a currency change in the history); two people saving for the same employee at the same moment both succeed (history is append-only, and ties go to the newest entry); there is no warning for a very large jump, and the percentage in the history is the check, after saving; the first-salary form (a person with no history) is covered by unit tests but was not looked at in a browser.
21. **The export.** *What it is:* the Export CSV button above the directory downloads everyone who matches the current search and filters, in the current sort order, as one file: employee ID, name, job title, level, department, country, joining date, status, the last day for someone who left, the currency, the annual salary in force today and the date it started, the same in US dollars, and the pay band. It is the whole set, not the page on screen (a test checks this, and fails if the filters are dropped or the page is sent). *How:* `QUERY /employees/export` takes the list's filter body without paging and answers with the file in one response; the app fetches it (the access token lives only in memory, so a plain link cannot carry it) and hands it to the browser to save, as `employees-YYYY-MM-DD.csv`. One query, built from the same filter and sort code as the list, so the file is exactly the directory the user was looking at. No job queue: a file of 10,000 people is 1.3 MB and takes a few seconds (see `performance.md`). *Why CSV and not .xlsx:* no library, the same bytes on every machine, and Excel opens it. Three details make that true for Excel: a UTF-8 byte order mark (without it Excel reads "Müller" as "MÃ¼ller"), CRLF line ends, and amounts and dates written exactly as stored ("48700.00", "2025-04-01"), never formatted by a locale. *Spreadsheet formulas:* a cell that starts with = + - @ (or a tab or carriage return) gets a leading apostrophe, because Excel would otherwise run a name or job title typed as `=HYPERLINK(...)` as a formula (CSV injection). The cost is that a value that genuinely starts with a minus or plus sign shows the apostrophe; amounts never do. *Not done:* an .xlsx file; choosing the columns; a progress bar (the button shows that it is working); a record of who exported what, which matters if salary data is sensitive; the real HTTP time for 10,000 people. A real-browser run against a mock API confirmed that the file is saved with the byte order mark, a header and exactly the people the filter selected; Excel itself was not opened.
22. **The bulk salary update (template, upload, preview, apply).** *Flow:* the Bulk update button on the directory opens a page with three steps: download a template, fill it in, choose the saved CSV and see every row checked. The preview saves nothing; applying is the last step. *The template* (`GET /salary-updates/template`) is everyone who can still be given a salary (not those who have left), one row each with their current salary, and three empty columns at the end: New annual salary, Effective from, Reason. The person fills in the three for the people getting a change and leaves the rest empty; a row with all three empty is ignored and only counted. *The preview* (`POST /salary-updates/preview`) takes the file as the request body with the type `text/csv` (read as text in the browser, so there is no multipart upload to handle; Express needed a reader for that type, limited to 6 MB, about 20,000 rows). It is stateless: nothing is stored, so there is no half-finished upload to clean up, and the browser sends the file again to apply it. The check is one pure function, so applying can run exactly the same check on the data as it is then. *Reading the file:* RFC 4180 CSV (quotes, doubled quotes, line breaks inside a cell, LF or CRLF, a leading byte order mark), with the delimiter sniffed from the header row because Excel saves with semicolons in many European settings; columns are found by name and ignoring case, spaces and punctuation, so extra columns are ignored and "employee_id" is "Employee ID"; every row keeps the line number it starts on, so a message says "line 7" and means the line in their spreadsheet. *What is refused* (each row can have several problems, all reported at once): an Employee ID that is missing, unknown or listed twice (every occurrence is refused, naming the lines), an amount that is not digits with an optional dot and at most two decimals, or is zero (a thousands separator or a currency symbol is refused rather than guessed), a date that is not a real YYYY-MM-DD (a date like 01/12/2026 is refused as ambiguous), a reason that is not one of the four, and then the app's single-change rules, unchanged: nobody who has left, not before the joining date, HIRE only for a first salary. A salary equal to the one in force today is "unchanged" and records nothing, so applying the same file twice cannot add anything the second time. A file that cannot be read at all (a missing column, no rows, more than 20,000 rows, a quote that is never closed) is reported as such and no row is checked. *Warnings* do not block: a raise above 50% (probably an extra zero or a dropped dot) and any decrease unless the reason is Correction. *Exact money:* the percentage is worked out in whole cents with BigInt and rounded half away from zero, the same as the database does for the history, so the preview and the history agree; the amount stays the text that was typed. *One definition of the salary in force:* the directory and this lookup share one SQL fragment, and the lookup asks it for each row's own effective date, so a row is judged against what the person is paid on that date (a raise already scheduled counts) and the currency is the one in force then, as for a single change. This was first built against today's salary, which would have added a raise dated next month a second time when the same file was applied again; a test that applies a future-dated file twice caught it before it shipped, and the fix is proved at full scale in `performance.md`. *On the page:* counts first (will be updated, already at that salary, with errors, to double-check, left empty), then the rows, opening on the ones that need a decision (errors and warnings), with tabs for the rest and a downloadable error report (one line per problem, with the line of their file); an Excel workbook is turned away before upload with what to do (Save As CSV); Excel can rewrite ISO dates, so the page says to format the date column as text. *Applying:* `POST /salary-updates/apply` takes the same CSV, runs the same check again on today's data (so a stale preview can never overwrite a salary changed in between) and, in one transaction, records one `imports` row (file name, a SHA-256 of the file, who applied it, when, and the counts of rows, added, unchanged and skipped) and adds a salary record, in batches of 1,000, for every row that passed; each record points back to the import and carries who applied it. Rows with errors are skipped, and the page asks the person to confirm what will be skipped and what carries a warning before the button works. When nothing would be added nothing is saved, not even an import. The table and its columns were reviewed by the author before the migration was written. *Not done:* two applies of one file at the same instant (both could add; the button is disabled while one runs, and there is one HR manager); `.xlsx` upload; a template limited to a filter; mapping the columns of a different file. A real-browser run against a mock API confirmed the loop: download the template, fill rows with mistakes on purpose, upload, see the counts and the right rows, download the error report; the mock's rules are a rough copy, the real ones are covered by tests.
23. **The sign-in cookie across sites.** *The problem:* the refresh token is a cookie set to `SameSite=Strict`, which a browser never sends from one site to another. With the site on GitHub Pages and the API on Render those are two sites, so the cookie would never be sent: every page reload and every expiry of the 15-minute access token would sign the user out. *The choice:* a setting, `REFRESH_COOKIE_SAMESITE` (`strict` by default, then `lax` or `none`), and `none` for the demo. A custom domain with the site and the API under one parent (`app.` and `api.`) would keep `Strict` and work in every browser, but needs a domain; a proxy would need the cookie path to be configurable. `none` works in Chrome, Edge and Firefox and not in Safari, which blocks third-party cookies, so a Safari user would still be signed out on reload. *What `none` costs, and how it is paid:* `Strict` was also what stopped another website making a visitor's browser call `/auth/refresh` and `/auth/logout` with the cookie attached (a hostile page could sign someone out). With `none` that protection is gone, so those two endpoints check the request's `Origin` header, which a page cannot forge: it must be one of `CORS_ORIGINS`, or the API's own host (its documentation page), or absent (a command-line client is not a page being used against its visitor). Anything else, including the literal `null` origin, gets a 403 before the cookie is read. The check runs whatever the setting is, so it also guards the default. *Forced HTTPS-only:* a browser rejects `SameSite=None` without `Secure`, so `none` always sets `Secure`, whatever `NODE_ENV` says; the clearing header uses the same flags, because a browser only deletes a cookie when they match. *Still not done:* the real thing in two browsers on two real hosts (the e2e tests check the headers and the guard, not a browser's behaviour across sites), and a custom domain, which is the way to make it work in Safari.

## Deliberately not chosen

- **Docker Compose** — the app is reviewed through the hosted URL and demo video, not run locally.
- **Microservices, message queues, caching layers** — unnecessary at 10k rows; they would add moving parts without changing the user's outcome.
- **An LLM feature** — not required by the brief; salary data is sensitive and should not be sent to a third party in v1.
